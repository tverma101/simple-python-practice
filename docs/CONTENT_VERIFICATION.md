# Content verification report

Generated by `tools/verify_content.py` against the Python-practice-platform
database (`coding_platform.db`). Regenerate with:

```bash
python tools/verify_content.py --db path/to/coding_platform.db --out reports/verification.json
```

To turn the same verdicts into the database the practice server actually serves,
use [`tools/build_content.py`](CONTENT_BUILD.md):

```bash
python tools/build_content.py --db path/to/coding_platform.db \
    --out content.db --report reports/build.json
```

The per-problem detail (2,529 quarantined rows) is written to
`reports/verification.json`, which is gitignored because it is 1.2 MB of
machine-generated detail. This file is the summary worth reading and reviewing.

## The number that matters

| | Count | Share |
|---|---|---|
| Problems imported | 5,132 | 100% |
| **Verified shippable** | **2,603** | **50.7%** |
| Quarantined | 2,529 | 49.3% |

**Half the imported library cannot be graded.** A student who opens a
quarantined problem would be given a starter file that does not parse, or tests
whose expected values are labels rather than answers, and would be marked wrong
for being right.

Test cases: of 30,511, **28,966 decode cleanly** (94.9%). A case is usable when
it parses — nothing more. See "Why usable means parseable" below.

### Why 2,603 and not the 2,547 this file used to claim

This file previously reported 2,547 verified / 2,585 quarantined, and before
that 2,550 / 2,582. Both were correct when written. The current verifier, from
both `tools/verify_content.py` and `tools/build_content.py`, produces
**2,603 / 2,529**. Two deliberate changes account for the movement.

**`TestCase.usable` now means "parses".** It previously also required non-empty
`args`/`kwargs`, which made every zero-argument function untestable: a signature
like `def to_uppercase() -> str:` is legitimately called as `to_uppercase()`, so
an empty argument list is the *correct* shape rather than a malformed row. That
rule excluded 920 of 30,511 cases — 3% of the library's tests — and left those
problems with nothing to grade against. Rows that are genuinely unusable still
fail: an empty `input_data`, an unparseable expected value, a JSON object with
no `args` key.

**The static AST allowlist now applies to reference solutions.** `verify_problem`
runs the same `check_student_code` filter the grader does, so a solution that
calls `eval` is rejected before it runs. That moved three problems the other way
than the fix above, and the net is +56:

| Problem | Title | Reference solution | Verdict before | Verdict now |
|---|---|---|---|---|
| `u8_calc` | Basic Calculator | `return eval(s)` | verified (2/2) | `sandbox_rejected` |
| `u8_calc2` | Basic Calculator II | `return eval(s)` | verified (2/2) | `sandbox_rejected` |
| `u8_calc3` | Basic Calculator III | `return eval(s)` | verified (2/2) | `sandbox_rejected` |

Those three solutions are one line long and are `eval`; with the allowlist
skipped they verify 2/2 and would ship, which is exactly how they reached the
earlier numbers. Rejecting them is correct: a student cannot be expected to pass
a problem whose only reasonable solution is `eval`, and a grader that refuses to
execute `eval` must not be able to have its answer supplied by the reference
implementation either.

A grader that will not run `eval` for a student cannot be handed an `eval` as
the answer it grades against — the two must use the same filter, or the
reference solution is a privileged path around the student's own restrictions.

So the headline is unchanged in substance — a little over half the library ships
— and the three problems that stopped shipping are the three that should never
have.

## What is actually wrong

Quarantined problems grouped by defect rather than by status, because status
answers "can this ship?" and defect answers "what has to change?" — and for most
of these they are not the same question.

| Defect | Count | What it means | Fixable by |
|---|---:|---|---|
| `row_unparseable` | 837 | Test rows could not be decoded, or no callable name | Re-authoring the test data |
| `starter_unparseable` | 535 | The starter file is not valid Python | Mostly mechanical |
| `expected_is_placeholder` | 337 | Expected output is scaffolding (`result`, or an echo of the input) | Automatic where unambiguous |
| `name_mismatch` | 289 | The signature names a function the solution does not define | Renaming |
| `mismatch` | 195 | Solution and expected output disagree, neither obviously a placeholder | Manual review |
| `expected_is_prose` | 184 | Expected output is a label (`Zero`, `Empty list`) | Automatic where unambiguous |
| `test_input_wrong_type` | 147 | A test feeds a string to a numeric parameter | Re-deriving inputs from the signature |
| `blocked_operation` | 3 | The solution reaches for `eval`; the grader's allowlist refuses it | Rewriting the solution |
| `solution_broken` | 1 | The reference solution genuinely does not work | Manual |
| `unknown` | 1 | The solution defines no function of the declared name, and it defines none at all | Manual |
| **Total** | **2,529** | | |

**Only one problem in 5,132 has a broken solution.** That is the headline. The
reference solutions are almost entirely fine; what is broken is the test data and
the starter files wrapped around them. Which is good news, because it means the
library is mostly repairable rather than mostly wrong.

## What the repair tool will and will not do

`tools/repair_content.py` fixes a problem **only** when every expectation that is
already a plausible answer still matches, and the expectation it rewrites is
provably not an answer. Under that rule it repairs 4 problems in the first 900
and declines 17.

Those 17 declines are the rule working, not the tool failing. A representative
case, `check-if-all-uppercase`:

* the declared signature is `def check_if_all_uppercase(sub, text):`
* the solution defines `is_all_upper(text)`
* the test cases pass `sub=`, which belongs to a different problem
* the expectations are `''`, `'Single character'`, `True`, `False`

Filling that in means guessing which of three disagreeing things is authoritative.
The tool declines, and the problem is reported as `name_mismatch` so a human can
settle it. Had the tool "fixed" it by recording whatever the solution returned, it
would have produced a problem that looks verified and tests nothing.

The practical consequence: **mechanical repair only works where the damage is
confined to the expectation column.** The larger `row_unparseable` bucket needs
re-authoring, and that is the work for the content-repair agents.

## Known content defects, by cause

These were read directly out of the source database and are reproducible:

* **330 starters** contain an unterminated triple-quoted string — a docstring
  opened and never closed.
* **105 starters** are a `def` line followed only by comments, so the body is
  empty and Python raises `IndentationError`.
* **53 starters** use a literal `...` in the *parameter list*
  (`def remove_item(...):`). The author appears to have meant an ellipsis body.
  For these the signature itself is the ellipsis, so the real parameters are
  unknown and the starter is left alone rather than guessed.
* **45 starters** are indented at module level with no enclosing block.
* Problems such as `absolute-value` receive `num='test'` and expect `'test'`.
  A correct implementation of `abs()` must raise on that input, so the reference
  solution is being blamed for the test's bad data.

## Why verification runs inside the sandbox

`verify.py` executes the reference solutions, so it uses the same
`ducky.sandbox` policy as the grader. That is deliberate: a verifier that ran
untrusted code more safely than the grader would be an odd place to draw the
line, and there is no reason for the two to diverge. See
[`docs/SECURITY_MODEL.md`](../docs/SECURITY_MODEL.md).

Verification is fast — the full 5,132-problem sweep, executing 3,275 reference
solutions, takes about 75 seconds at a pool of 8. Building the servable
`content.db` from the same verdicts takes the same again, plus under a second to
write. See [`CONTENT_BUILD.md`](CONTENT_BUILD.md).
